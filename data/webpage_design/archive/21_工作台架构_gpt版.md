# 钱博士投研工作台整体架构



## 1. 架构原则



1. **保真优先，摘要可再生**：原始视频、ASR 全文、时间戳、说话上下文不可覆盖；结构化笔记、观点、日报都是可版本化的派生数据。

2. **先单体，后拆分**：一个 FastAPI 服务 + 一个后台 Worker 进程 + PostgreSQL/SQLite 起步。不要一开始上 Kafka、微服务、复杂 Agent 平台。

3. **事实、观点、推理分层存储**：行情/公告是事实，分析师说法是观点，Agent 结论是独立推理，三者不能混为一层。

4. **所有结论可追溯**：前端展示的每条结论都必须能回答：`来源是什么、何时产生、依据哪些证据、模型如何推理、是否使用实时数据`。

5. **租户隔离从第一天进入数据模型**：即使当前只有一个正式用户，也必须让用户私有数据带 `tenant_id/user_id`。

## 3. 核心数据设计：解决信息保真



### 3.1 不要把“摘要”当作原始事实



现有链路应从：



```text

直播 -> ASR -> 结构化笔记 -> 观点

```



改为：



```text

原始视频/音频

  -> ASR 原始结果（逐词时间戳、置信度、分段）

  -> 语义片段 Transcript Segment

  -> 推理单元 Reasoning Unit

  -> 观点 Claim

  -> 工作台卡片/日报/回答

```



其中，前一级永不被后一级覆盖。后一级只保存“引用关系”和“解释关系”。



### 3.2 五类关键对象



| 对象 | 作用 | 是否允许 AI 改写 |

|---|---|---|

| `raw_asset` | 视频、音频、新闻原文、公告 PDF/HTML | 不允许 |

| `transcript_segment` | ASR 片段，保留起止时间、原文、置信度、说话人 | 仅允许人工/二次校正生成新版本 |

| `reasoning_unit` | 一个完整论证单元：结论、依据、条件、反例、上下文 | 可生成，但必须保留原文引用 |

| `claim` | 可比较、可跟踪的原子观点，例如“碳酸锂供给仍过剩” | 可生成、可失效、可被修订 |

| `research_output` | Agent 回答、日报、资产卡、决策建议 | 可再生成，不能成为唯一证据 |



`reasoning_unit` 是保真设计的核心，不要直接从全文压缩为观点。它至少包括：



```json

{

  "thesis": "碳酸锂价格反弹不代表供需反转",

  "premises": ["库存仍在累积", "新增产能尚未出清"],

  "conditions": ["需求端没有超预期政策刺激"],

  "counter_arguments": ["若下游补库持续超过两周，需要修正判断"],

  "asset_refs": ["碳酸锂", "锂矿", "电池ETF"],

  "source_segment_ids": ["seg_101", "seg_102", "seg_103"],

  "source_time_range": ["01:12:08", "01:15:47"]

}

```



### 3.3 证据图，而不是单纯 RAG



建立轻量“证据图”，存 PostgreSQL 关系表即可，不需要图数据库：



```text

Research Output

   ├── based_on -> Claim

   ├── based_on -> Market Fact / News / Announcement

   └── cites -> Reasoning Unit

                     └── derived_from -> Transcript Segment

                                               └── belongs_to -> Raw Asset

```



每个 `claim` 要有：



- `speaker_type`：分析师、Agent、用户、外部机构。

- `stance`：看多、看空、中性、观察。

- `confidence`：置信度，不等于正确率。

- `valid_from / valid_until`：观点有效窗口。

- `conditions`：成立条件。

- `falsifiers`：证伪条件。

- `evidence_ids`：不可为空，除非明确标为“Agent 假设”。



### 3.4 检索策略：先找推理链，再找摘要



用户问“为什么说碳酸锂供给过剩”时，检索顺序应为：



```text

资产/主题识别

  -> Claim 检索

  -> Reasoning Unit 检索

  -> 找回相邻 ASR 片段（前后各 1~2 段）

  -> 找回对应新闻/公告/行情事实

  -> LLM 组织回答，并附证据编号

```



不能只对“日报摘要”做向量检索，否则会反复放大压缩失真。



对 ASR 使用“语义片段 + 相邻窗口”：



- 分段以话题转换、停顿、资产实体变化为边界，不单纯按固定字数切块。

- 每个片段保留 `previous_segment_id / next_segment_id`。

- 检索命中后自动扩展上下文，避免只截取一句造成断章取义。

- ASR 低置信度片段标记风险，前端显示“转写待确认”，Agent 不应把它作为高置信证据。

## 4. 多源消息输入设计



### 4.1 第一批接入源



| 类别 | 建议来源 | 接入频率 | 用途 |

|---|---|---:|---|

| 分析师内容 | B站直播、录播、用户上传音频/文本 | 实时/日更 | 观点与推理链 |

| A 股/ETF 行情 | 合规行情 API、券商/数据商接口 | 分钟级 | 异动、持仓联动 |

| 期货/商品 | 碳酸锂、黑色、有色、原油等行情接口 | 分钟级 | 产业链验证 |

| 新闻 | 财经资讯 API、RSS、指定媒体 | 5~15 分钟 | 事件驱动 |

| 公告 | 巨潮、交易所公告、上市公司 IR | 小时级/日更 | 基本面与风险事件 |

| 宏观 | 国家统计局、央行、海关、官方日历 | 日/月 | 宏观变量验证 |

| 用户输入 | 持仓、观察列表、手工研究笔记 | 即时 | 个性化分析 |



不要在 MVP 阶段爬取大量不稳定、版权不清晰的网站。每个数据源都实现统一 `SourceAdapter`：



```python

class SourceAdapter:

    source_name: str



    async def fetch(self, cursor: str | None) -> list[RawDocument]: ...

    async def normalize(self, raw: RawDocument) -> list[NormalizedEvent]: ...

```



### 4.2 统一事件模型



所有外部输入先写入 `source_event`，再由后续任务解析：



```text

source_event

- id, source_type, source_name, source_url

- published_at, fetched_at

- raw_content_uri, content_hash

- entities: 股票/ETF/商品/行业/宏观指标

- event_type: 行情异动/新闻/公告/直播/宏观发布

- reliability_level

- parse_status

```



`content_hash` 用于去重；`published_at` 与 `fetched_at` 分开，用于避免把“晚抓到的旧新闻”误判为新信息。



### 4.3 与分析师观点交叉验证



系统不应让 Agent 简单判定“分析师对/错”，而应输出四种状态：



| 状态 | 含义 |

|---|---|

| `supported` | 新事实支持原观点的关键前提 |

| `challenged` | 新事实冲击原观点的关键前提 |

| `unrelated` | 事件相关性弱，不足以改变判断 |

| `pending` | 数据不足，继续观察 |



示例：



```text

分析师观点：锂价反弹不代表供需反转

关键前提：库存继续累积、供给未明显收缩



新事件：某锂盐厂宣布减产

交叉验证：challenged

原因：供给收缩方向与原前提相反，但单一厂商减产不足以推翻行业判断

待观察：减产规模、其他厂商跟随情况、社会库存周度变化

```



这类“前提校验”比对新闻做情绪摘要更有用。

## 5. Agent 独立分析逻辑



### 5.1 三个 Agent 角色，不做泛化大 Agent



| Agent | 任务 | 主要依据 |

|---|---|---|

| `Analyst RAG Agent` | 还原“分析师怎么想” | 分析师推理链、观点时间线 |

| `Independent Analysis Agent` | 对未覆盖资产形成独立判断 | 行情、新闻、公告、宏观、行业框架 |

| `Portfolio Risk Agent` | 基于用户持仓识别暴露与风险 | 持仓、成本、仓位、关联资产观点 |



统一由 `Research Orchestrator` 调度。用户问题先分类：查观点、查事实、独立研究、持仓风险、决策复盘；不要每次对话都跑全部工具。



### 5.2 独立分析框架



先把分析逻辑固化为可审计模板，再让 LLM 填充，而不是让模型自由发挥：



```text

1. 资产定义：标的、行业位置、核心驱动变量

2. 当前状态：价格/估值/基本面/政策/资金面

3. 多空论点：每边至少列出可验证依据

4. 关键变量：哪些数据变化会改变判断

5. 情景推演：基准、乐观、悲观

6. 证伪条件：什么发生时当前结论失效

7. 行动边界：观察、等待确认、风险提示；不直接替用户下单

```



输出分为三层：



```text

事实层：行情、公告、新闻、宏观数据

推理层：Agent 如何从事实推导结论

结论层：当前判断、置信度、风险与证伪条件

```



模型生成的推理必须引用工具返回的证据 ID。无证据部分明确标记为“分析假设”，避免伪造事实。



### 5.3 LLM 分工与控制



- `deepseek-v4-flash`：分类、实体抽取、事件去重、初步结构化、普通问答。

- `gpt-5.6-sol`：复杂研究、跨源冲突分析、复盘、需要长推理链的问题。

- 高级模型调用前，先用检索和规则缩小上下文；3500 token 预算只投给“高价值决策”。

- Agent 每轮最大工具数、最大时间窗口、最大引用数可配置，防止成本和延迟失控。

- 对话不直接暴露完整 CoT；前端展示的是“可审计推理摘要 + 证据链 + 工具调用记录”。

## 6. 多用户隔离与权限



### 6.1 租户模型



内测阶段采用：



```text

User -> Workspace(个人工作区) -> Private Data

                         └────> Shared Research Space(平台公共研究库)

```



- 平台采集的分析师直播、行情、公告、公开研究：进入 `shared` 数据域。

- 用户持仓、成本、决策记录、私聊、个人笔记、导出文件：进入私有工作区。

- 用户可以收藏公共观点到自己的工作区，但不能修改公共原始资料。

- 后续企业版再扩展 `Organization -> Workspace -> Members`。



### 6.2 数据库隔离规则



所有私有表必须带：



```text

workspace_id

created_by

visibility: private | workspace | shared

```



包括 `portfolio_position`、`decision_record`、`chat_session`、`research_note`、`export_job`。



FastAPI 服务层通过依赖注入获取当前身份：



```python

current_user -> current_workspace -> repository query filter

```



任何 Repository 查询必须显式接收 `workspace_id`，禁止前端传入任意用户 ID 后直接查询。



### 6.3 认证与权限



MVP 推荐：



- 邮箱验证码或密码登录。

- JWT access token + refresh token。

- 角色：`admin`、`beta_user`、`viewer`。

- `admin` 可管理公共数据源和用户配额，不能默认查看用户私有持仓与决策。

- 审计日志记录：登录、导出、查看私有决策、Agent 调用、管理员操作。

- 对话和导出接口按用户限流，避免内测用户拖垮高级模型预算。

## 7. 前端交互设计



### 7.1 页面结构



```text

左侧：工作区 / 市场 / 资产 / 观点 / 持仓 / 决策 / 数据源

中部：当前研究内容或对话主视图

右侧：证据链、引用来源、工具执行记录、相关资产

```



避免做成传统聊天机器人页面。默认入口应是“今日工作台”。



### 7.2 核心视图



| 页面 | 主要内容 |

|---|---|

| 今日工作台 | 盘前重点、持仓变化、昨夜新增观点、待验证前提、风险事件 |

| 资产研究页 | 资产卡、多空卡、分析师观点、Agent 独立判断、观点时间线 |

| 证据抽屉 | 原文、ASR 时间轴、相邻上下文、新闻/公告出处、跳转原视频 |

| 研究对话 | 自由提问，回答以可折叠结构化研究报告呈现 |

| 持仓与决策 | 持仓、关联观点、决策记录、证伪提醒、复盘结果 |

| 过程审计 | 本次 Agent 调用的工具、数据时间、缓存命中、模型、耗时 |



### 7.3 卡片与对话的组合



对话回答不只输出文本，而是输出可渲染块：



```text

[结论卡] 当前判断与置信度

[多空卡] 看多/看空理由及证据数量

[证据卡] 原文引用、来源、时间、可靠性

[风险卡] 证伪条件和待观察数据

[行动卡] 加入观察、创建决策、订阅提醒

```



每张卡片可展开到 `reasoning_unit`，再下钻到 ASR 原文和视频时间点。这样卡片服务快速浏览，对话服务探索，证据抽屉服务信任。



### 7.4 工具调用可视化



对高级分析任务展示简洁执行轨迹：



```text

已查询：碳酸锂期货行情（10:31 更新）

已检索：钱博士近 30 日相关直播（命中 6 段）

已读取：2 条行业新闻、1 份公司公告

结论：基于 9 条证据生成，存在 2 个待验证假设

```



不要展示模型内部思维过程；展示用户可验证的“数据和操作轨迹”。

## 8. 技术落地建议



```text

frontend/        React + TypeScript + Vite + TanStack Query + Zustand

backend/         FastAPI + SQLAlchemy + Alembic + Pydantic

worker/          APScheduler 起步；任务变多后切 Celery + Redis

database/        PostgreSQL + pgvector

object-storage/  MinIO（开发）/ 云对象存储（生产）

cache/queue/     Redis

deployment/      Docker Compose + Nginx/Caddy

observability/   structlog + Sentry + 简单任务后台页

```



现有 ChromaDB 可以继续使用，但新功能建议逐步迁移到 `PostgreSQL + pgvector`：业务关系数据、权限过滤、向量检索在同一数据库，单人维护成本更低。迁移期间保留 ChromaDB 为旧索引，双写并逐步切读。

## 9. 分期路线



### Phase 0：数据底座重构，1~2 周



目标：先止住信息损失。



- 保留原始视频、音频、完整 ASR JSON。

- 引入 `transcript_segment / reasoning_unit / claim / evidence_link`。

- 将现有结构化笔记和日报改成派生数据。

- 建立资产实体标准化与来源 ID。

- 给旧数据补迁移脚本，允许历史资料逐步回填。



验收：任一日报观点可下钻到直播原文时间点。



### Phase 1：可用 MVP，2~4 周



目标：自己每天能用的工作台。



- FastAPI + React 基础工作台。

- 登录、个人工作区、持仓和决策隔离。

- 分析师内容接入、证据链检索、资产页、研究对话。

- 接入行情、新闻、公告三类外部源。

- 支持“今日盯什么”“为什么这么判断”“我的持仓状态”。



验收：用户可从盘前卡片进入资产页，再进入 ASR 原文；持仓不会被其他用户访问。



### Phase 2：内测版本，3~5 周



目标：让小范围用户稳定使用。



- Agent 独立研究模板与多空分析。

- 分析师观点与新事件的前提校验。

- SSE 流式回答、任务状态和工具调用可视化。

- 用户配额、限流、审计日志、异常告警。

- 订阅提醒：持仓关联事件、观点被挑战、证伪条件触发。

- 决策记录与基础复盘。



验收：用户问未被直播覆盖的股票，Agent 能给出明确事实、假设、风险和引用，不能只输出泛泛摘要。



### Phase 3：付费准备，后续迭代



目标：形成可计费的 Agent 服务能力。



- 工作区套餐、模型额度、数据源权限。

- 高级研究报告与 Markdown/PDF 导出。

- 分析师历史观点追踪、命中率与条件化复盘。

- 公共/私有研究分享权限。

- OpenAPI / MCP Server，供外部工具调用。

- 企业团队工作区和组织级权限。

## 10. 最关键的实施边界



1. **不要让 LLM 直接写入“事实库”**。LLM 输出只能写入观点、推理或报告，并携带证据引用。

2. **不要删除原始 ASR 与上下文**。即使转写质量不好，也应保留版本与置信度，校正后新增版本。

3. **不要把“分析师观点”和“Agent 判断”混在一个字段里**。二者的责任主体、证据标准、可信度不同。

4. **不要一开始做全自动交易或明确买卖指令**。当前产品应定位为研究、风险提示与决策复盘工具。

5. **优先做可追溯研究闭环**：输入事件 → 推理链 → 观点 → 用户决策 → 结果复盘。这个闭环形成后，再扩大数据源和 Agent 能力。

> 生成者：老手（独立生成，未参考 gpt 版）
> 日期：2026-08-29
> 目标：多用户、混合交互（卡片+对话）、多源消息、Agent 独立分析、**信息保真**

---

## 0. 核心设计哲学

**三条铁律：**

1. **保真 > 压缩**（解决"分析师逻辑被消磨"）
   现有管道：直播 → ASR → 结构化笔记 → 观点抽取，每层都"总结"，推理链逐层丢失。
   新架构：**原始证据永久保存 + 分层观点 + 推理链显式建模**。
   任何总结都有"父指针"指回更原始的材料，Agent 可随时下钻到 ASR 原文。

2. **观点与证据分离**
   观点（claim）= 结论；证据（evidence）= 支撑该结论的推理链/原文/数据。
   一个观点可以有多条证据，一条证据可以支撑多个观点。
   Agent 回答必须带证据引用（你已有的铁律，架构级固化）。

3. **消息源可插拔 + 分析框架可配置**
   分析师直播只是消息源之一。新闻/行情/公告/宏观是平级源。
   Agent 的分析逻辑 = 可配置的分析框架（不是写死在 prompt 里）。

## 2. ★ 信息保真设计（核心，解决你最大的痛点）★

### 问题本质
```
直播音频(丰富推理) → ASR(丢语气) → LLM总结(丢推理过程) → 观点(只剩结论)
```

### 方案：证据片段库（Evidence Snippets）

**核心思路：ASR 转写完成后，不急着"总结成笔记"，先按语义切句，把每一段推理保留为"证据片段"，然后才做结构化。每个观点/笔记条目记录 `evidence_ids` 指向这些片段。**

数据模型：

```
evidence_snippets 表
├─ id            (ev_xxx)
├─ bvid          来源视频
├─ ts_start/end  时间戳（可跳转到视频位置！）
├─ speaker       分析师
├─ text          原文片段（ASR 纠错后）
├─ topic         话题标签（LLM 打标）
├─ entities      [碳酸锂, 宁德时代]（LLM 抽取）
├─ claim_refs    [view_xxx]（被哪些观点引用，反链）
└─ created_at

structured_views 表（现有，改造）
├─ ...现有字段
├─ evidence_ids  [ev_xxx, ev_yyy]  ← 新增：指向证据片段
└─ parent_id     可嵌套（观点→子论点）

notes 表（现有笔记）
└─ evidence_ids  [ev_xxx]  ← 新增
```

**检索时**：Agent 回答"为什么碳酸锂供给过剩"→ RAG 命中观点 view_123 → 沿 evidence_ids 下钻到 ev_045（钱博士原话片段，含时间戳）→ 展示原文 + "点击跳转视频位置"。

**保真承诺**：任何一层总结都可以展开回原始材料，最多跳一跳就能看到分析师原话。**推理链不再消失，只是被索引了。**

### 实现成本（关键：不用重写现有管道）
- transcribe_to_note.py 增加一步：ASR 完成后先调 `evidence_extractor.py`（LLM 切句+打标，flash 即可）→ 存 evidence_snippets → 再走现有结构化
- 现有笔记/观点表加 evidence_ids 列（迁移脚本，已有先例）
- **不破坏现有日报/复盘链路**，纯增量

## 3. 多源消息输入（N1）

### 消息源抽象

```
MessageSource (协议)
├─ AnalystLiveSource    分析师直播（现有，保真改造）
├─ NewsSource           财经新闻（B站动态/雪球/东财 API）
├─ AnnouncementSource   上市公司公告（东财/巨潮）
├─ MarketSource         行情异动（现有 market_cache + 盘中轮询）
├─ MacroSource          宏观日历（CPI/PMI/利率决议）
└─ (可插拔：加一个源 = 实现一个类 + 配置一行)
```

每条消息统一 schema：
```
{source, type, ts, entities[], text, raw_url, importance(0-1)}
```

### 消息消化管线
```
多源消息 → 统一入消息库 → 增量 Topic 聚合器(LLM, flash) 
→ 更新观点库的"新变化"标记 → Agent 盘前速览/会话时自动注入
```

### 与分析师观点的关系（交叉验证）
- **分析师观点** = 有署名、有立场、历史可追溯（你的差异化资产）
- **实时消息** = 无立场事实（新闻/公告/行情）
- Agent 回答 = 消息(事实) + 观点(立场) + 自己的分析(推理) 三者分离标注
  - 例："碳酸锂今日 -2.1%（**消息**）；钱博士 8.27 认为供给过剩未变（**观点**）；按六因子框架，供需因子偏空（**我的分析**）"

## 4. Agent 独立分析逻辑（N2）

### 分析框架 = 可配置的多因子检查清单

```
分析框架 schema (JSON, 可编辑)
{
  "name": "投研六因子",
  "factors": [
    {"id": "supply_demand", "name": "供需", "prompt": "查供给增量/需求增速证据"},
    {"id": "cycle", "name": "景气周期", "prompt": "判断当前周期位置"},
    {"id": "valuation", "name": "估值", "prompt": "对比历史分位"},
    {"id": "capital", "name": "资金", "prompt": "资金流向/拥挤度"},
    {"id": "policy", "name": "政策", "prompt": "政策/监管动向"},
    {"id": "risk", "name": "风险", "prompt": "列下行风险"}
  ]
}
```

**Agent 分析流程**（讨论工作台没有的股票时）：
1. 用户问"XX 怎么看" → 意图识别：工作台无此资产 → 走"独立分析"
2. 按六因子逐项：每因子 → 查消息库(实时) + 查 RAG(历史观点) + 查行情
3. 每因子产出一段带证据的结论
4. 汇总：因子一致性 → 综合判断 + 分歧标注 + 风险
5. 输出格式：**和资产分析卡同构**（这样有/无数据的资产展示一致）

### 与"只会转述"的区别
现有模式：Agent = 检索器 + 复读机（分析师说啥它说啥，逻辑被消磨）
新模式：Agent = 检索器 + **推理器**（用框架组织证据，补全缺失环节，标注"无数据项"）

## 5. 多用户隔离（内测）

### 数据模型
```
users 表：id, email, role(admin/member), invite_code, quota
user_portfolios 表：user_id, symbol, shares, cost, note  ← 用户自己维护
user_decisions 表：user_id 隔离（现有决策库加 user_id 列）
workspace_prefs 表：user_id, watchlist, theme
```

### 隔离原则
- **公共层**（观点库/证据库/消息库/RAG）= 所有用户共享只读（这是产品资产，不隔离）
- **私有层**（持仓/决策/偏好/会话）= 按 user_id 严格隔离
- 所有 API：JWT 解码 → user_id 注入 → SQL 查询强制 `WHERE user_id = ?`
- 内测：邀请码注册（admin 生成），配额表限流（每日查询次数）

### 为什么这样分
观点库是"公共情报"，持仓决策是"私有判断"——内测用户花钱买的是**情报+分析**，不是互相看仓位。

## 6. 前端交互设计（卡片 + 对话混合）

### 布局
```
┌────────┬──────────────────────────────┬────────┐
│ 侧边栏  │  主区（卡片流）                │ 对话区  │
│ 会话列表 │  资产卡/多空卡/证据链/复盘卡   │ Agent  │
│ 持仓    │  ▲▼ 滚动                      │ 对话   │
│ 关注板块 │                              │ (流式) │
└────────┴──────────────────────────────┴────────┘
```

### 混合交互模式
- **点卡片 → 出结论**（面板式）：点"半导体"→ 资产卡渲染（快，确定性）
- **问对话 → 出结论+卡片**（对话式）：问"半导体现在什么情况"→ Agent 回答 + **内嵌卡片**（Markdown 里渲染卡片组件）
- **卡片 → 追问**：卡片上的"证据链"按钮 → 下钻视图（原文片段+时间戳）
- **工具调用轨迹**（汲取 DSH）：对话中每次工具调用显示为可展开行（工具名/参数/返回摘要），点开看详情——过程可视化

### 卡片类型
| 卡片 | 数据源 | 触发 |
|---|---|---|
| 资产卡 | asset_card_builder 现有 | 点资产/对话命中 |
| 多空对照卡 | debate_card_builder 现有 | 同上 |
| 证据链卡 | 新（evidence_ids 下钻） | 卡片内按钮 |
| 决策复盘卡 | decision_review 现有 | 决策相关对话 |
| 消息流卡 | 消息库（新） | 盘前速览/关注板块 |
| 独立分析卡 | Agent 六因子（新） | 非库内资产 |

## 7. 与现有系统的关系（渐进迁移，不推翻）

```
现有 (E:\qianboshi-agent)          新增 (E:\qianboshi-workbench)
├─ 采集/ASR/结构化/日报      ──复用──▶  管道原样，加 evidence_extractor
├─ RAG/观点库/决策库         ──复用──▶  加列迁移，不动主表
├─ 飞书推送                 ──保留──▶  生产链路不动
└─ Hermes cron              ──保留──▶  调度不动
                                   新增工作台 = 独立的 FastAPI + React 项目
                                   通过 API 访问现有数据（不动现有脚本）
```

**关键决策：工作台是"读现有库的新服务"，不是"现有管道的新壳"。**
现有脚本（cron/日报/飞书）继续跑，工作台只是多一个消费者。风险最低。

## 9. 关键风险与对策

| 风险 | 对策 |
|---|---|
| 证据片段库存储膨胀 | 片段只存文本+元数据（KB 级），音频不复制；超期归档 |
| LLM 成本（六因子×N 资产） | flash 打底，只有综合判断走 sol；结果缓存（T+1 同资产不重算） |
| 多用户权限漏洞 | 所有查询强制 user_id 参数化；内测白名单；写操作审计日志 |
| 现有管道改动影响日报 | evidence_extractor 独立步骤，失败不阻塞主链路（降级：无片段也能跑） |
| 消息源 API 不稳定 | 源适配器隔离 + 重试 + 缓存；一个源挂了不影响其他 |

​# 钱博士 Agent 求职作品集展示方案

核心叙事建议：不要把页面做成“AI 功能清单”，而要让面试官沿着一条完整链路看到：**内容采集 → 观点结构化 → 可检索知识 → 预测与回测 → 决策记录 → 到期复盘**。所有页面都围绕“系统真实运行、数据可验证、结果可复盘”展开。

## ① 数据可视化选型

### 首页概览

| 数据 | 推荐图表 | 展示目的 |
|---|---|---|
| 9473 条结构化观点 | 大数字 + 小型趋势折线图 | 第一眼体现规模与持续运行状态 |
| 9400+ RAG chunks | 大数字 + 分段进度条 | 体现知识库不是静态 Demo |
| 900+ 篇笔记 | 大数字 + 月度柱状图 | 体现从原始内容到结构化产物的转化 |
| 3 万+ 回测预测事件 | 大数字 + 预测事件时间轴 | 体现系统具有历史验证能力 |
| 6 个财经 UP 主 | 横向来源列表 + 头像/来源标识 | 说明数据来源真实且可追溯 |
| 59.6% 看空命中率 vs 39.1% 看多命中率 | 双柱对比图或哑铃图 | 用最少视觉元素突出关键洞察 |
| 数据处理链路 | 横向 pipeline stepper | 让首页直接呈现系统闭环 |

首页不要堆放过多图表。建议首屏只放系统名称、核心运行指标、数据链路和一条具有解释力的回测结论。

### 系统架构页

架构页重点不是统计图，而是可读、可追踪的系统拓扑：

- 使用分层架构图：`采集层 → 处理层 → 智能层 → 存储层 → 输出层`。
- 每层使用节点卡片，展示技术名称和实际职责，例如 `yt-dlp`、`faster-whisper GPU`、`ASR纠错`、`DeepSeek`、`ChromaDB`、`飞书 API`。
- 用带方向的连线表达数据流，连线上的标签可标注输入输出格式，例如“音视频”“转写文本”“结构化观点”“向量检索”。
- 对定时任务用时间轴或 cron 节点表现；对 MCP 工具使用工具列表或能力矩阵，不建议画成无意义的装饰性图标。
- 节点悬停时显示输入、输出、失败处理和运行频率，能直接体现工程完整度。

### 数据资产页

| 数据资产 | 推荐图表 | 交互建议 |
|---|---|---|
| 6 个内容来源 | 横向条形图 | 按视频数、观点数或笔记数切换排序 |
| 观点的多空分布 | 发散条形图 | 多空使用红绿，未知/中性使用灰色 |
| 观点数量随时间变化 | 面积图或柱线组合图 | 支持按来源、主题、资产筛选 |
| 观点主题分布 | Treemap 或横向条形图 | 主题数量较多时优先横向条形图，便于读标签 |
| RAG chunk 规模 | 分层条形图 | 展示来源、文档、chunk 的层级关系 |
| 笔记处理状态 | 堆叠柱状图 | 区分已转写、已纠错、已结构化、已入库 |
| 预测事件 | 时间轴 + 事件点 | 点击事件查看预测方向、目标日期和结果 |
| 来源质量 | 来源对比表 + 命中率条形图 | 同时显示样本数，避免只看百分比 |

数据资产页可以模拟真实终端，但每个图表必须支持“解释数据”的操作。建议提供统一筛选器：时间范围、来源、资产、方向、处理状态。筛选结果应同步影响顶部指标、图表和明细表。

### 决策台页

决策台应体现“今天能用”，而不只是展示历史数据：

- 顶部使用市场状态栏：更新时间、数据覆盖时间、今日观点数、待复盘数量、数据健康状态。
- 5 张资产卡使用白底产品风格，卡片内展示资产名称、当前判断、多空信号、置信度、信号数量、最近更新时间和风险提示。
- 资产卡上的多空信号用发散条形图或水平能量条，不要只用一个红绿标签。
- 资产间观点对照使用矩阵：行是资产，列是来源/分析师，单元格显示看多、看空、中性和信号强度。
- 预测目标与实际结果使用区间图或事件时间轴：预测日期、目标日期、到期结果应在同一条线上展示。
- 盘前简报使用“摘要 + 证据”结构。摘要展示结论，证据区域列出引用笔记、原始视频时间戳和相关观点。
- 关键指标之间的关系可用散点图展示，例如样本数量与命中率，避免把小样本的高命中率误认为可靠优势。

资产卡建议保持固定高度和稳定网格尺寸。卡片内部即使数据为空、加载中或出现错误，也不能让其他卡片跳动。

### 实盘纪律页

这一页应该突出决策过程和复盘能力：

- 决策日志：使用按日期排列的垂直时间轴，每条记录显示当时判断、依据、风险、执行状态和到期结果。
- 预测复盘：使用预测区间与实际收益的对照图，清晰区分“尚未到期”“命中”“失效”“无法判断”。
- 命中率：使用带样本数的区间条或子弹图。不要只使用一个大百分比。
- 多空表现：使用双向收益曲线或分组柱状图，直接展示看空与看多策略的差异。
- 错误分析：使用混淆矩阵，区分方向判断错误、时间判断错误、目标幅度错误和缺少有效结果。
- 纪律指标：使用小型 KPI 表格，例如“已到期预测数”“自动复盘率”“无依据决策数”“人工修改率”。

这页最重要的是展示系统会记录错误，而不是只挑选成功案例。

## ② 动效与交互建议

### 滚动动效

- 首页的采集到复盘链路使用分段进入动画，随着滚动逐步点亮节点和数据流。
- 架构页使用分层 reveal：进入某一层时，该层节点高亮，其他层降低对比度；不要持续自动播放复杂动画。
- 数据资产页可让顶部指标在首次进入视口时从快照值平滑计数到最终值，但必须在无障碍模式下关闭。
- 实盘纪律页的决策时间轴可随滚动逐步展开，并在到期节点显示复盘结果。
- 深浅色页面之间切换时使用短时的背景和边框过渡，避免整页闪烁或过长的全屏转场。

动画时长建议控制在 `160ms-360ms`。复杂图表只在首次进入或用户主动切换时动画，数据更新时不要反复重播。

### 悬停与点击

- 图表悬停显示精确值、时间范围、样本数和数据来源。
- 资产卡悬停显示最近的两到三条证据摘要；点击后进入右侧详情抽屉，而不是把用户带离当前决策上下文。
- 架构节点点击打开详情面板，内容包括技术角色、输入输出、运行频率、异常处理和相关代码模块。
- 观点事件点击后显示原始内容引用、视频时间戳、结构化字段和向量检索结果。
- 图表图例应可点击隐藏/显示系列，筛选条件应同步反映在 URL 或页面状态中，方便面试时复现某个视图。
- 所有陌生图标提供 tooltip；导出、筛选、刷新、展开、复制等操作使用图标按钮并配合可访问名称。

### 切换交互

- 中英双语切换应保持当前路由、筛选条件、滚动位置和图表状态。
- 数据资产页提供“概览 / 明细”切换；决策台提供“盘前摘要 / 证据 / 历史复盘”标签页。
- 统计口径切换时，明确标注口径，例如“按观点数”“按事件数”“按到期事件数”。
- 深浅色切换采用显式主题按钮，并记忆用户选择；架构页和金融终端页的深色主题应使用独立 token，而不是简单把白色页面反相。
- 页面加载、空状态、错误状态和数据过期状态都要有明确界面。静态快照模式下应显示快照时间，避免用户误以为数据是实时的。
- 提供 `prefers-reduced-motion` 支持，关闭计数、连线流动和滚动 reveal 等非必要动效。

## ③ 求职展示重点

### 面试官应第一眼看到的内容

1. **真实数据规模**：9473 条观点、900+ 篇笔记、3 万+预测事件不是口号，应能点击进入明细或看到生成时间、来源和统计口径。
2. **完整工程链路**：从 B 站源采集到飞书推送，明确展示每一步解决了什么问题。
3. **AI 不只是调用模型**：突出 ASR 纠错、结构化抽取、向量检索、证据引用、失败重试和数据质量控制。
4. **可验证结果**：59.6% 和 39.1% 必须同时展示样本数、时间区间、命中定义和统计方法。
5. **决策闭环**：系统不仅生成观点，还记录决策、等待到期、自动复盘，并保留错误结果。
6. **个人贡献边界**：明确哪些模块由你设计、开发、调试和维护，哪些是第三方服务或基础设施。
7. **工程取舍**：解释为什么使用 `yt-dlp`、`faster-whisper GPU`、`ChromaDB`、SQLite、cron 和 MCP，以及这些选择的限制。

建议首页放一个“系统运行事实”区域，例如：最近采集时间、最近处理视频数、最近一条盘前简报、最近一次复盘结果。它比泛泛的“AI 驱动洞察”更有说服力。

### 应避免的问题

- 不要用大面积渐变、浮夸的 AI 视觉元素或营销文案稀释系统细节。
- 不要把所有数字做成孤立的大数字，必须提供时间、来源、样本数和口径。
- 不要把“命中率”直接写成投资收益率，也不要暗示系统可以稳定预测市场。
- 不要只展示成功预测；错误预测、未到期事件和无法判断事件同样要可见。
- 不要把架构图画成技术名词墙。每个组件都要有输入、输出和职责。
- 不要让“实盘”表述超过实际能力。如果系统没有自动下单或实时行情，应使用“决策支持”“观点复盘”这类准确表述。
- 不要把 MCP、RAG、Agent 当成卖点本身，要说明它们如何改善检索、操作效率或复盘流程。
- 不要使用未经验证的实时数据或伪造运行状态。作品集可以使用静态快照，但必须明确快照时间和数据来源。

## ④ 技术实现建议

### 前端框架

推荐：**Next.js + TypeScript + Tailwind CSS + shadcn/ui + Apache ECharts**。

- Next.js 负责多页面路由、静态生成和服务端/客户端边界。
- TypeScript 用于约束 API 响应、图表数据和双语文案 key。
- Tailwind 适合快速建立白色产品页、暗色架构页和金融终端页的设计 token。
- shadcn/ui 提供可控的抽屉、标签页、表格、tooltip、菜单等基础组件。
- ECharts 更适合金融图表、时间轴、散点图、矩阵和复杂 tooltip；普通趋势图也可使用 Recharts，但项目中最好保持图表库数量收敛。
- 使用 `lucide-react` 作为图标库。
- 使用 TanStack Query 处理 API 模式下的请求、缓存、刷新和错误状态；静态快照模式可通过同一数据访问接口替换数据源。

### 设计系统

建议定义三层 token：

- 基础 token：颜色、间距、字号、边框、阴影、动效时长。
- 语义 token：`surface-page`、`surface-panel`、`text-primary`、`text-muted`、`signal-up`、`signal-down`、`status-warning`。
- 页面主题 token：`theme-product`、`theme-architecture`、`theme-terminal`。

页面通过 `data-theme` 切换主题，而不是在组件中散落硬编码颜色：

```css
[data-theme="product"] {
  --surface-page: #f7f8fa;
  --surface-panel: #ffffff;
  --text-primary: #17191c;
  --border-subtle: #dfe3e8;
  --signal-up: #16805c;
  --signal-down: #c74444;
}

[data-theme="terminal"] {
  --surface-page: #111416;
  --surface-panel: #191d20;
  --text-primary: #e8eceb;
  --border-subtle: #30373a;
  --signal-up: #43c58a;
  --signal-down: #ef6666;
}
```

涨跌颜色需要配合文字、图标或方向符号，不能只依赖颜色传递信息。深色终端页应控制对比度，避免高饱和红绿覆盖整个界面。

### i18n 双语

建议使用 `next-intl`，语言路由采用 `/zh` 和 `/en`。所有页面文案、图表标题、tooltip、空状态、错误信息和日期格式都进入翻译资源，不要在组件内写三元表达式。

```text
app/
  [locale]/
    page.tsx
    architecture/page.tsx
    data-assets/page.tsx
    decision-desk/page.tsx
    discipline/page.tsx
    about/page.tsx
messages/
  zh.json
  en.json
```

图表数据中的分类字段也应使用稳定 key，再由前端翻译，例如 `bullish`、`bearish`、`neutral`，不要把中文字符串直接作为业务判断条件。

### FastAPI 只读 API + 静态快照双模式

前端统一使用 `DataProvider` 接口，运行时通过环境变量选择 API 或快照实现：

```text
frontend/
  app/
    [locale]/
      page.tsx
      architecture/page.tsx
      data-assets/page.tsx
      decision-desk/page.tsx
      discipline/page.tsx
      about/page.tsx
  components/
    charts/
    assets/
    architecture/
    decision/
    layout/
    ui/
  lib/
    api-client.ts
    snapshot-client.ts
    data-provider.ts
    i18n.ts
    theme.ts
  public/
    snapshots/
      overview.json
      architecture.json
      assets.json
      decisions.json
      discipline.json
  messages/
    zh.json
    en.json

backend/
  app/
    main.py
    api/
      routes/
        overview.py
        architecture.py
        assets.py
        decisions.py
        discipline.py
    schemas/
      overview.py
      assets.py
      decisions.py
    services/
      read_model.py
      snapshot_exporter.py
    repositories/
      sqlite_repository.py
    core/
      config.py
      logging.py
  scripts/
    export_snapshot.py
  tests/
    test_read_api.py
    test_snapshot_schema.py
```

推荐的 API 设计：

```text
GET /api/v1/overview
GET /api/v1/architecture
GET /api/v1/assets?from=...&to=...&source=...&direction=...
GET /api/v1/decisions?asset=...&status=...
GET /api/v1/discipline?from=...&to=...
GET /api/v1/health
```

接口只读，返回统一结构：

```json
{
  "data": {},
  "meta": {
    "generated_at": "2025-01-01T08:00:00Z",
    "as_of": "2025-01-01",
    "source": "snapshot",
    "version": "2025.01.01"
  }
}
```

`DataProvider` 应保证两种模式返回相同 schema：

```ts
export interface DataProvider {
  getOverview(): Promise<OverviewData>;
  getArchitecture(): Promise<ArchitectureData>;
  getAssets(filters: AssetFilters): Promise<AssetsData>;
  getDecisions(filters: DecisionFilters): Promise<DecisionsData>;
  getDiscipline(filters: DisciplineFilters): Promise<DisciplineData>;
}
```

静态快照适合作品集部署、离线演示和稳定截图；FastAPI 模式适合本地面试演示和展示筛选、刷新、错误处理。快照由脚本从 SQLite 或只读分析库生成，前端绝不直接读取生产数据库。

### 实现优先级

1. 先完成首页、数据资产页和决策台，建立“规模、证据、闭环”的主叙事。
2. 再补架构页和实盘纪律页，解释工程实现与复盘方法。
3. 最后完善双语、快照导出、错误状态、可访问性和响应式细节。
4. 在发布前准备一套固定演示数据，确保面试时不依赖外部服务、网络或实时任务。

最终作品集应让面试官能在三分钟内回答四个问题：**数据从哪里来、系统如何处理、结果如何验证、你具体做了什么。**
